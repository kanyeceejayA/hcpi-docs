    Python for the HCPI Platform

    Duration: ~1 hour, deliberately slow. Audience: Developers who already write code in some other language (Java, C#, PHP, JavaScript, Go, …) and need just enough Python to be productive inside HCPI. Outcome: You'll recognise every Python idiom HCPI uses and be able to read any model file without getting stuck on syntax.

    This is not a beginner-from-zero tutorial. We skip "what is a variable" and focus on the parts that look different from what you already know.

    Setup — a scratch folder for practising

    Everything in this hour runs outside HCPI. Use a throwaway folder so you can't accidentally break your install:

    mkdir -p ~/python-practice
cd ~/python-practice

    You have two ways to run code:

    The REPL — interactive, great for trying one line at a time:

    python3
>>> 1 + 1
2
>>> exit()

    A .py file — for anything more than two lines:

    # practice.py
print("hello")

    python3 practice.py

    Pick whichever feels more comfortable. The REPL is faster for the snippets in this page; switch to a file when an exercise asks you to.

    Use the HCPI venv if you want

    source /opt/hcpi/venv/bin/activate activates HCPI's Python. It's the exact same interpreter HCPI runs on — handy if you want library versions to match. Not required for anything on this page.

    1. Variables and types — the parts that surprise other-language devs

    x = 5            # int
y = 3.14         # float — no separate "double"
name = "Alice"   # str — single or double quotes are identical
flag = True      # bool — capital T/F, NOT lowercase
nothing = None   # the null/nil/undefined equivalent

    Three things that catch newcomers from typed languages:

    1. No declarations. Just assign. Re-assigning to a different type is legal:

    x = 5
x = "now I'm a string"  # fine — variables are just labels for values

    2. Truthiness is broad. if value: is true for non-zero numbers, non-empty strings, non-empty lists/dicts, and anything that isn't None/False/0/""/[]/{}. You'll see this everywhere in HCPI — e.g. if record.outlet_id: checks "does this record have an outlet linked", because an empty Many2one is "falsy".

    >>> bool([])
False
>>> bool([0])
True   # a list with one element is truthy, even if that element is falsy
>>> bool("")
False
>>> bool("False")
True   # the *string* "False" is non-empty, so truthy

    3. None is not False. None == False is False. Always test with is None if you mean "missing":

    if value is None: ...
if value is not None: ...

    f-strings — the way to format

    Forget %s / .format(). Modern Python uses f-strings:

    name = "Alice"
n = 5
print(f"Hello {name}, you have {n} reports.")
# Hello Alice, you have 5 reports.

# Inline expressions are allowed:
print(f"Doubled: {n * 2}")

# Format specifiers after a colon:
pi = 3.14159
print(f"{pi:.2f}")   # 3.14
print(f"{42:>5}")    # right-aligned in width 5: "   42"

    You'll see plain string concatenation ("hi " + name) in older code; prefer f-strings in anything you write.

    Exercise 1

    Open the REPL and figure out:

    • What does bool("0") return? Why is it surprising?
    • What does None == None return? What does None is None return?
    • Build an f-string that says "Alice has 5 outlets (average price: $12.34)" using variables.

    2. The four collection types

    items = ["bread", "milk", "eggs"]           # list  — ordered, mutable
prices = ("USD", 1.0)                       # tuple — ordered, immutable
unique = {"bread", "milk", "milk"}          # set   — unordered, unique
person = {"name": "Alice", "age": 30}       # dict  — key→value mapping

    List — the workhorse

    items = ["bread", "milk", "eggs"]

items[0]            # "bread"  — zero-indexed
items[-1]           # "eggs"   — negative indexing counts from end
items[1:3]          # ["milk", "eggs"] — slice (start inclusive, end exclusive)

items.append("rice")             # add at end
items.insert(0, "salt")          # insert at index 0
items.remove("milk")             # remove first match
del items[0]                     # remove by index
len(items)                       # length

"bread" in items                 # True/False — membership check

    Lists are passed by reference. Just like objects in Java/JS:

    a = [1, 2, 3]
b = a
b.append(4)
print(a)   # [1, 2, 3, 4]  — both names point to the same list

    Dict — the second workhorse

    person = {"name": "Alice", "age": 30}

person["name"]                  # "Alice"
person["email"]                 # KeyError!
person.get("email")             # None  — safe lookup
person.get("email", "n/a")      # "n/a"  — with default

person["email"] = "a@b.com"     # add or update
del person["age"]               # remove

person.keys()                   # dict_keys(['name', 'email'])
person.values()                 # dict_values(['Alice', 'a@b.com'])
person.items()                  # dict_items([('name', 'Alice'), ('email', 'a@b.com')])

"name" in person                # True — checks keys, not values

    Dicts are everywhere in Odoo. Every create() call takes a dict; every action returns a dict; every domain is a list of tuples but the values it operates on are stored in dict-like records.

    Tuple — when you want "fixed pair/triple"

    point = (10, 20)
x, y = point         # unpacking — also works on lists

    You'll see tuples for domains in Odoo: ('field_name', '=', value) is a 3-tuple.

    Set — when you need uniqueness

    tags = {"food", "drink", "food"}    # {"food", "drink"}
tags.add("snack")
tags.discard("missing")             # no error if absent
"food" in tags                       # O(1) — much faster than `in list` for big collections

    • Make a dict mapping each outlet name to a price (a float). Add a new outlet. Print all (name, price) pairs.

    3. Control flow

    if / elif / else

    if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
else:
    grade = "C"

    No parentheses around the condition. Indentation defines the block. Four spaces. Mixing tabs and spaces is a parse error — pick spaces and stick with them.

    There's no switch. For "match one of many values", chained elif is idiomatic. Python 3.10+ has match/case but Odoo code rarely uses it.

    for

    for item in items:
    print(item)

for i in range(5):              # 0, 1, 2, 3, 4
    print(i)

for i in range(2, 8, 2):        # 2, 4, 6 — start, stop, step
    print(i)

for name, age in [("Alice", 30), ("Bob", 25)]:
    print(name, age)             # unpacks each tuple

for i, item in enumerate(items):
    print(i, item)               # i is the index

for k, v in person.items():
    print(k, "=", v)             # iterate dicts as pairs

    There's no C-style for(i=0; i<n; i++). Use range() or enumerate().

    while

    n = 5
while n > 0:
    print(n)
    n -= 1

    break and continue work as in C/Java.

    Comprehensions — the most "Pythonic" thing

    This is the single biggest syntax difference from other languages. Read it carefully because it's all over Odoo:

    # List comprehension — build a list from another iterable
squares = [x * x for x in range(5)]
# [0, 1, 4, 9, 16]

# With a filter
evens = [x for x in range(10) if x % 2 == 0]
# [0, 2, 4, 6, 8]

# Dict comprehension
prices_doubled = {k: v * 2 for k, v in prices.items()}

# Set comprehension
unique_lengths = {len(name) for name in items}

    In Odoo you'll constantly see things like:

    # Get all outlet names from a recordset
names = [outlet.name for outlet in outlets]

# Map outlets by id
by_id = {outlet.id: outlet for outlet in outlets}

# Filter records that match a condition
active = [o for o in outlets if o.active]

    The mental model: read it right-to-left. [x for x in things if cond] = "for each x in things, if cond, collect x into a list."

    Exercise 3

    • Write a dict comprehension that maps 1→"odd", 2→"even", 3→"odd", 4→"even" for numbers 1 to 5.
    • Given names = ["alice", "BOB", "Charlie"], build a list with each name lower-cased and longer than 3 chars.

    4. Functions

    def greet(name):
    return f"Hello, {name}"

print(greet("Alice"))

    Default arguments

    def greet(name, greeting="Hello"):
    return f"{greeting}, {name}"

greet("Alice")                    # "Hello, Alice"
greet("Alice", greeting="Hi")     # "Hi, Alice"
greet("Alice", "Hey")             # positional also fine

    *args and **kwargs

    When you see these in Odoo code, here's what they mean:

    def log(*args, **kwargs):
    print("positional:", args)     # tuple of extra positional args
    print("keyword:", kwargs)      # dict of extra keyword args

log(1, 2, 3, level="info", user="alice")
# positional: (1, 2, 3)
# keyword: {'level': 'info', 'user': 'alice'}

    This is how Odoo's super().create(*args, **kwargs) calls work — they pass everything on to the parent method without caring what the parameters are.

    Lambdas — tiny inline functions

    square = lambda x: x * x
square(5)                         # 25

# More commonly used inline:
sorted_outlets = sorted(outlets, key=lambda o: o.name)

    You'll see lambdas in Odoo defaults and filters:

    date = fields.Date(default=lambda self: fields.Date.today())

    That lambda self: is a function that takes a recordset and returns today's date. Odoo calls it each time a new record is created.

    Exercise 4

    • Write a function total(prices, discount=0) that returns the sum of a list of prices minus a percentage discount.
    • Use sorted() with a lambda to sort the list [("apples", 2), ("milk", 1.5), ("bread", 3)] by price (the second element).

    5. Modules and imports

    Files are modules; folders with __init__.py are packages. You import them by name:

    import math                       # whole module
math.sqrt(9)                      # 3.0

from math import sqrt             # just one name
sqrt(9)                           # 3.0

from math import sqrt, pi         # multiple
from math import sqrt as s        # alias

    In Odoo, you'll see imports like:

    from odoo import fields, models, api
from odoo.exceptions import UserError, ValidationError

    That's just "from the odoo package, get the fields, models, and api sub-modules". api contains decorators like @api.depends.

    Your own modules

    Create helpers.py in ~/python-practice/:

    def double(x):
    return x * 2

    Then in another file or the REPL in the same folder:

    import helpers
helpers.double(5)        # 10

from helpers import double
double(5)                # 10

    Exercise 5

    Create ~/python-practice/calc.py with two functions add(a, b) and multiply(a, b). Then create main.py that imports them and prints add(2, 3) and multiply(2, 3).

    6. Classes — just enough for Odoo

    You don't need deep OOP fluency to work in Odoo, but you do need to recognise these patterns.

    class Outlet:
    def __init__(self, name, code):
        self.name = name
        self.code = code

    def label(self):
        return f"{self.code}: {self.name}"

o = Outlet("Kikuubo", "K01")
print(o.label())                  # "K01: Kikuubo"

    Things to notice:

    • __init__ is the constructor (Python's new equivalent).
    • Every method takes self as the first argument — the instance the method's called on. You don't pass it explicitly when calling (o.label(), not o.label(o)) but you must declare it.
    • No private / public keywords. Convention: prefix with _ to mean "internal, don't touch from outside".
    • Inheritance: class SpecialOutlet(Outlet):. Call the parent with super().method().

    What Odoo models look like (preview)

    from odoo import fields, models

class Outlet(models.Model):
    _name = 'hcpi.outlet'
    _description = "Outlet"

    name = fields.Char(required=True)

    def label(self):
        return f"{self.outlet_code}: {self.name}"

    Reading this with the Python you now know:

    • class Outlet(models.Model) — inherit from models.Model (a class Odoo provides).
    • _name, _description — class attributes Odoo's framework reads.
    • name = fields.Char(...) — assigning a Field object to a class attribute. Odoo's metaclass turns this into a database column at install.
    • def label(self): — instance method. The self here is special: in Odoo it's a recordset (zero or more records), not a single object.

    That's the whole class system you need.

    Exercise 6

    Write a class Report with attributes name and date, a method summary() returning "Report <name> for <date>". Create two instances and print their summaries.

    7. Exceptions

    try:
    result = 10 / 0
except ZeroDivisionError as e:
    print(f"Bad math: {e}")
except (ValueError, TypeError):
    print("Bad input")
else:
    print("No error")             # runs if no exception
finally:
    print("Always runs")

    Raise your own:

    raise ValueError("Negative price not allowed")

    In Odoo, you'll see specific exception types:

    from odoo.exceptions import UserError, ValidationError

if price < 0:
    raise UserError("Price must be non-negative")

    UserError shows the message to the user as a friendly dialog. ValidationError is similar but used in @api.constrains. Don't catch these — let them propagate to the UI.

    8. Decorators — for @api.depends

    A decorator is a function that wraps another function. The syntax is:

    @my_decorator
def some_function():
    pass

    You won't write decorators yourself for a while. But you will apply Odoo's:

    from odoo import api, fields, models

class Outlet(models.Model):
    _name = 'hcpi.outlet'

    name = fields.Char()
    code = fields.Char()
    full_label = fields.Char(compute='_compute_full_label')

    @api.depends('name', 'code')
    def _compute_full_label(self):
        for record in self:
            record.full_label = f"{record.code}: {record.name}"

    What @api.depends('name', 'code') does: "this method computes the full_label field, and Odoo should re-run it whenever name or code changes." That's it. You'll see this on every computed field.

    Other Odoo decorators you'll meet:

    • @api.constrains('field_name') — validation that runs on save.
    • @api.onchange('field_name') — runs in the UI as the user types.
    • @api.model — method operates on the model class itself, not on records.

    9. Idioms you'll see in HCPI code

    A grab-bag of patterns that look weird the first time:

    Ternary expression:

    label = "active" if record.active else "archived"

    Walrus operator (Python 3.8+, occasional in modern code):

    if (n := len(items)) > 10:
    print(f"Too many items: {n}")

    Unpacking in function calls:

    args = [1, 2, 3]
kwargs = {"sep": "-", "end": "!\n"}
print(*args, **kwargs)       # 1-2-3!

    with statements (context managers):

    with open("file.txt") as f:
    content = f.read()
# file is closed automatically when block exits

    get() with default — instead of if "key" in dict:

    # verbose:
if "name" in record:
    name = record["name"]
else:
    name = "unknown"

# Pythonic:
name = record.get("name", "unknown")

    enumerate and zip together:

    names = ["a", "b", "c"]
ages = [1, 2, 3]
for i, (name, age) in enumerate(zip(names, ages)):
    print(i, name, age)

    10. What you should be able to do now

    You should be able to:

    • Read any HCPI model file and recognise every line as Python (even if you don't know what specific Odoo APIs do).
    • Spot a list/dict/tuple/set at a glance.
    • Write a one-liner with a list comprehension.
    • Write a small class with a couple of methods.
    • Recognise an f-string, a decorator, and a lambda.
    • Open the Python REPL and try things out interactively.

    If any of those still feel shaky, the cure is practice, not more reading. The exercises in this page take ~30 minutes if done in order.

    Python Equivalent in other langs
    None null, nil, undefined
    True / False always capitalised
    f"text {var}" `text ${var}` (JS), String.format (Java), printf (C)

    dict.get(k, default) map.getOrDefault(k, default)
    is None / is not None == null / != null
    def f(*args, **kwargs) varargs + keyword args
    lambda x: x * 2 (x) => x * 2 (JS), x -> x * 2 (Java)
    len(x) x.length / x.size()
    "a" in list_or_dict_or_str .contains(...) / .includes(...)
    print(x) console.log / System.out.println
    # comment //
    4-space indent defines blocks { } defines blocks
